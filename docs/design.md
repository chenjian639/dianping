# 校园预约取餐：设计与验收

## 为什么引入时段产能

库存回答“还有多少份菜”，时段名额回答“这一刻能处理多少单”。两个资源分别计数，每单只占一个时段名额。当前不根据菜品复杂度分配权重，也不允许多档口合单。

名额统计包含待支付、已支付、制作中、待取餐和已完成订单。已取消订单不占用。完成订单保留名额，防止同一时段的容量被循环复用；过期时段不再接受新预约。

## 事务边界

```text
锁定用户行（与购物车修改共用）
  → 查询幂等结果；同键同时间段则返回旧订单
  → 读取购物车并校验同档口
  → 条件占用时段名额（档口营业、未来时段、仍有余量）
  → 插入订单，数据库计算支付截止时间
  → 按菜品 ID 升序条件扣库存并插入价格快照
  → 删除当前用户购物车
  → 插入超时检查 Outbox
提交；任意异常则整体回滚
```

不在用户购买链路引入 Redis 预扣、分布式事务或微服务拆分。单数据库事务能直接保证这里的核心不变量，便于观察行锁和验证正确性。用户行锁也避免多实例、不同幂等键重复购买同一份购物车，以及下单清空购物车时误删并发新增项。

`requestId` 标识一次购买尝试。请求成功后无论订单处于何种状态，复用同一键返回原订单；想购买新购物车必须生成新键。相同键改时段拒绝。当前没有购物车内容指纹；客户端应在变更购买内容后使用新键。

## 订单状态与资源

| 转换 | 原子裁决 | 名额/库存 |
| --- | --- | --- |
| 下单 | 用户锁、唯一约束、容量/库存条件更新 | 同事务扣减 |
| 支付 | user_id + 待支付 + expires_at > NOW() | 保持占用 |
| 用户取消 | user_id + 待支付 | 同事务归还 |
| 超时取消 | 待支付 + expires_at <= NOW() | 同事务归还；未抢到状态直接返回 |
| 开始制作/待取餐 | restaurant_id + 预期旧状态 | 保持占用 |
| 核销 | restaurant_id + 待取餐 + pickup_code | 完成后仍计入已消耗产能 |

支付是模拟状态转换。没有支付渠道到账语义，也不能把此处的状态竞争结论推广为真实支付资金一致性。

## 缓存与消息

持久补偿队列用于删除共享 Redis；删除后向 fanout exchange 发布本地失效，每实例绑定独立匿名队列。不能让多个实例争抢一个共享队列来完成广播。

匿名队列适合活跃实例缓存通知，断线时不提供持久消息重放。当前版本没有彻底解决“旧值回填覆盖失效”的竞态，不能声称强一致或端到端 30 秒陈旧上界。时段可用余量直接查数据库，下单通过数据库条件更新确认，不依赖缓存展示值。

Outbox 至少一次投递仍可能在确认后、标记 SENT 前重复发布。超时取消以数据库状态为幂等依据。广播重复删除本地缓存无副作用。投递失败达到上限后保留 FAILED 供排查；失败事件管理界面尚未实现。

## 统一的写入与缓存边界

餐厅信息、营业状态、评价三个写入口都在业务事务中调用 OutboxEventService.restaurantChanged。该组件使用 MANDATORY 传播，禁止脱离事务单独写入事件。先持久化Outbox，再发布本地事件；本地监听器只在提交后失效Caffeine。回滚保留旧缓存，Outbox写入失败则回滚业务和评分。MQ/Redis操作留在事务外的消费链路。

当前保留多级缓存及广播，用于验证跨实例行为。未声称解决旧值并发回填竞态或断线通知丢失；这部分仍是最终一致性边界，后续有性能证据再决定是否进一步精简L1。

## 评分口径

V3新增rating_sum，从评价表回填rating_sum、review_count和average_rating。新增评价时用一条原子SQL先计算ROUND((rating_sum+rating)/(review_count+1),1)，再递增总分和数量。average_rating是兼容查询与排序的派生字段，不再参与下一次计算。

搜索、详情、摘要统一读取餐厅行内统计，去掉详情路径重复聚合评价表的跨Service依赖。1、1、2、1四次评价总分5、数量4，统一得到1.3，而不是逐次舍入后的1.2。

## 调度与接口边界

SchedulingConfig使用两个独立、各单线程的调度器。outbox-每5秒投递，recovery-每30秒恢复卡住事件、每60秒扫描过期订单；发布循环等待确认不占用恢复线程。调度器由Spring管理生命周期，不再混用默认@Scheduled线程。

JWT在Spring Security的过滤链解析并建立SecurityContext，路由统一授权商家和管理员。资源归属仍通过用户/档口ID约束业务SQL；MerchantAccess只检查商家绑定，控制器不再复制角色规则。JSON错误体保留原结构，HTTP状态与code一致，内部异常不会伪装成401或200。

Controller统一经Service查询；用户行锁移动到UserMapper。购物车修改统一校验菜品状态/库存；取消共用资源归还方法。订单列表使用OrderSummaryVO，不让数据库实体决定对外字段。保留数据库回源的独立Bean以确保Bulkhead代理生效，没有为形式上的分层增加接口与实现空壳。

## 迁移与兼容

V1/V2保持不变。V3回填历史统计并生成详情失效事件。旧版本不维护rating_sum，不能在V3后继续混跑旧写入算法；回退需恢复备份或重新校正统计。部署前备份，数据库不自动回滚。

## 可复现证据

- `mvn clean verify`：单元测试与真实 MySQL 集成测试，包含并发竞争、失败回滚和旧库 baseline 迁移。
- `docker compose -f compose.campus.yml up -d --build` 后运行 `python scripts/smoke_campus.py`：两个真实 JVM、共享 MySQL/Redis/MQ、Nginx，测试跨实例预约、核销、取消、权限、缓存广播。
- 两套环境分别验证数据库事务行为和应用装配，不等同于生产吞吐测试。负载脚本的业务断言通过不代表拥有某个 QPS 能力。
