# 校园预约取餐：设计与验收

## 为什么引入时段产能

库存回答“还有多少份菜”，时段名额回答“这一刻能处理多少单”。两个资源分别计数，每单只占一个时段名额。当前不根据菜品复杂度分配权重，也不允许多档口合单。

名额统计包含待支付、已支付、制作中、待取餐和已完成订单。已取消订单不占用。完成订单保留名额，防止同一时段的容量被循环复用；过期时段不再接受新预约。

## 事务边界

```text
锁定用户行（与购物车修改共用）
  → 查询幂等结果；同键同时间段则返回旧订单
  → 读取购物车并校验同档口
  → 条件占用时段名额（档口营业、未来时段、仍有余量）
  → 插入订单，数据库计算支付截止时间
  → 按菜品 ID 升序条件扣库存并插入价格快照
  → 删除当前用户购物车
  → 插入超时检查 Outbox
提交；任意异常则整体回滚
```

不在用户购买链路引入 Redis 预扣、分布式事务或微服务拆分。单数据库事务能直接保证这里的核心不变量，便于观察行锁和验证正确性。用户行锁也避免多实例、不同幂等键重复购买同一份购物车，以及下单清空购物车时误删并发新增项。

`requestId` 标识一次购买尝试。请求成功后无论订单处于何种状态，复用同一键返回原订单；想购买新购物车必须生成新键。相同键改时段拒绝。当前没有购物车内容指纹；客户端应在变更购买内容后使用新键。

## 订单状态与资源

| 转换 | 原子裁决 | 名额/库存 |
| --- | --- | --- |
| 下单 | 用户锁、唯一约束、容量/库存条件更新 | 同事务扣减 |
| 支付 | user_id + 待支付 + expires_at > NOW() | 保持占用 |
| 用户取消 | user_id + 待支付 | 同事务归还 |
| 超时取消 | 待支付 + expires_at <= NOW() | 同事务归还；未抢到状态直接返回 |
| 开始制作/待取餐 | restaurant_id + 预期旧状态 | 保持占用 |
| 核销 | restaurant_id + 待取餐 + pickup_code | 完成后仍计入已消耗产能 |

支付是模拟状态转换。没有支付渠道到账语义，也不能把此处的状态竞争结论推广为真实支付资金一致性。

## 缓存与消息

持久补偿队列用于删除共享 Redis；删除后向 fanout exchange 发布本地失效，每实例绑定独立匿名队列。不能让多个实例争抢一个共享队列来完成广播。

匿名队列适合活跃实例缓存通知，断线时不提供持久消息重放。当前版本没有彻底解决“旧值回填覆盖失效”的竞态，不能声称强一致或端到端 30 秒陈旧上界。时段可用余量直接查数据库，下单通过数据库条件更新确认，不依赖缓存展示值。

Outbox 至少一次投递仍可能在确认后、标记 SENT 前重复发布。超时取消以数据库状态为幂等依据。广播重复删除本地缓存无副作用。投递失败达到上限后保留 FAILED 供排查；失败事件管理界面尚未实现。

## 可复现证据

- `mvn clean verify`：单元测试与真实 MySQL 集成测试，包含并发竞争、失败回滚和旧库 baseline 迁移。
- `docker compose -f compose.campus.yml up -d --build` 后运行 `python scripts/smoke_campus.py`：两个真实 JVM、共享 MySQL/Redis/MQ、Nginx，测试跨实例预约、核销、取消、权限、缓存广播。
- 两套环境分别验证数据库事务行为和应用装配，不等同于生产吞吐测试。负载脚本的业务断言通过不代表拥有某个 QPS 能力。
